## How to read

- **declared floor** — the scenario's `min_model_tier:` frontmatter (absent → treated as `judgment`, shown as `untiered`).
- **result @ tier** — PASS / FAIL from the most recent run at that tier; `below-floor` results are informational (failure expected below the declared floor).
- **verdict** — ✅ when the scenario passes at its declared floor; ❌ when it fails at its declared floor (a spec bug: raise the floor or simplify the prompt). ❌ rows block release per `/verify-release` check 12.

**Harness validity findings** (candidate upstream issues):
- Non-hermetic boot: on machines with co-installed skills/hooks, `-p` tier runs get hijacked (three distinct hijack paths observed in 7 runs). The run-eval spec needs a hermetic-boot story (`CLAUDE_CONFIG_DIR` relocates auth and is not viable as-is).
- 3 of 8 tier-annotated scenarios (`v1.8.7-b5-evals-required`, `v1.8.7-e9-status-line`, `v1.9-migration-correctness`) have no `## User Message` section — per run-eval spec they'd grade `FAIL (schema error)` at any tier. Excluded from this population run; they need runnable prompts or a `manual-rubric` marking.
- Remediation per spec for the two ❌ rows: raise `min_model_tier` to `judgment` *after* a confirming judgment-tier run, or harden the scenario-adjacent prompts (ROUTER batch-import routing; retrospective Step 0.5 output contract) for execution-tier reliability.

## Generation procedure (executed by /run-eval --tier, step 3)

1. After a tier run completes, collect per-scenario results from `evals/outputs/<scenario>-tier-<tier>-<timestamp>.md` (latest timestamp per scenario+tier wins).
2. Merge with existing rows for tiers not covered by this run (a run at one tier never erases another tier's column).
3. Rewrite the Matrix table: one row per scenario that has ≥1 tier result, sorted alphabetically; stamp `last run` with the run date.
4. Verdict column: compare the declared-floor column's result — PASS → ✅, FAIL → ❌, floor column not yet run → `pending`.
