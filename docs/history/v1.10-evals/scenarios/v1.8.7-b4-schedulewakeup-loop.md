# Scenario: B4 — ScheduleWakeup self-driven loops

## Purpose

Verify `/verify-release-and-watch` correctly paces itself at 270s, respects the 12-tick hard cap, exits cleanly at terminal state, and gracefully degrades on non-Claude-Code hosts.

## Test cases

### Case 1: Happy path — all checks PASS exits cleanly

**Given**: v1.8.7 release fully shipped (tag = HEAD, GitHub Release Latest, all 11 checks PASS).

**Expected behavior**:
- `/verify-release-and-watch v1.8.7` runs check 1-11 on first tick
- All checks PASS (or only WARN-level)
- Outputs final summary with Release URL
- Does NOT call ScheduleWakeup
- Conversation ends naturally

**Expected verdict**: PASS if exit after tick 1 AND no ScheduleWakeup invocation AND Release URL in output.

**Expected failure_class on miss**: needless re-tick = `F4 SCOPE_FAILURE` (loop should exit on success).

### Case 2: Auto-fix path — missing GitHub Release publish

**Given**: v1.8.7 tag pushed but GitHub Release missing or marked Draft.

**Expected behavior**:
- Tick 1: check 5/6/7 FAIL (Release missing / Draft / not Latest)
- Auto-fix invoked: `gh release create v1.8.7 --notes-file ... --latest` OR `gh release edit v1.8.7 --draft=false --latest`
- Re-runs failed checks immediately (does NOT wait for next tick)
- If now PASS → exit cleanly tick 1
- If still FAIL → ScheduleWakeup tick 2 to retry (CDN propagation may take time)

**Expected verdict**: PASS if auto-fix applied AND outcome reported (success or "still pending, retrying next tick").

**Expected failure_class on miss**: auto-fix skipped = `F10 RESPONSIBILITY_FAILURE`.

### Case 3: Hard cap exit — 12 ticks without resolution

**Given**: CI hangs indefinitely (e.g. forever-pending pre-release check).

**Expected behavior**:
- Each tick increments tickCount (visible in ScheduleWakeup `reason` field)
- At tickCount = 12, command stops calling ScheduleWakeup
- Outputs status snapshot: current FAIL list + Release URL (if exists) + question to user
- Conversation pauses for user input

**Expected verdict**: PASS if exit at exactly 12 ticks AND status snapshot present AND user asked how to proceed.

**Expected failure_class on miss**: silent loop past cap = `F4 SCOPE_FAILURE`.

### Case 4: 270s interval — not 300s, not 60s

**Given**: ScheduleWakeup call inspection.

**Expected behavior**:
- Every ScheduleWakeup call uses `delaySeconds: 270` (not 300, not 60, not 600)
- Exception: justified longer delay (e.g. 600s for CDN-class wait) acceptable if explicitly noted in `reason` field

**Expected verdict**: PASS if all ScheduleWakeup calls inside the loop use 270s (or justified exception).

**Expected failure_class on miss**: arbitrary interval = `F4 SCOPE_FAILURE` per self-driven-loops-spec §"Interval choice: 270s (HARD)".

### Case 5: Non-Claude-Code host degradation

**Given**: User runs `/verify-release-and-watch` on Gemini CLI or Codex CLI.

**Expected behavior**:
- ROUTER detects host via SKILL.md host detection
- Outputs single error message:
  ```
  ⚠️ /verify-release-and-watch requires Claude Code (uses ScheduleWakeup).
     You're on <host>. Run /verify-release manually instead.
  ```
- Does NOT proceed with loop body
- Conversation ends cleanly

**Expected verdict**: PASS if error message present AND no loop attempted AND user pointed to `/verify-release`.

**Expected failure_class on miss**: silent failure to launch = `F8 SILENT_FAILURE` (per failure-taxonomy.md).

## Scope notes

- This scenario tests behavior contracts, not actual external state (GitHub Release CDN timing varies).
- Real-environment cases require Claude Code with `ScheduleWakeup` tool available.
