# /migrate-soul-v2

Interactive migration of SOUL.md from v1 schema to v2 schema per `references/soul-spec.md` v2. **Idempotent**: re-running on a partially-migrated SOUL adds v2 YAML for any v1 dim that lacks it; never overwrites existing v2 YAML.

## Pre-flight

### 1. Locate SOUL.md
```bash
SOUL_PATH="${1:-}"
if [ -z "$SOUL_PATH" ]; then
  if [ -f "./SOUL.md" ]; then
    SOUL_PATH="./SOUL.md"
  elif [ -f "$HOME/SecondBrain/SOUL.md" ]; then
    SOUL_PATH="$HOME/SecondBrain/SOUL.md"
  fi
fi
```
If still not found → emit `❌ SOUL.md not found; pass path as $ARGUMENTS or cd into vault root first` and exit.

### 2. Backup before any change
```bash
cp "$SOUL_PATH" "${SOUL_PATH}.v1-backup-$(date +%Y%m%d-%H%M%S)"
```

### 3. Inventory existing v1 dimensions
Read SOUL.md and parse all v1 YAML blocks (look for `dimension:` field — that's the v1 marker). List dim names.

### 4. Check for existing v2 YAML
Look for `id: dv-*` and `formulation:` fields — that's v2 marker. If a v1 dim already has a matching v2 block → skip it (idempotent).

## Per-dimension migration loop

For each v1 dim without v2 block:

### Step 1: Show user the v1 entry

```
── Migrating dim: "<dimension name>" ──
Current v1 entry:
  dimension: "<name>"
  what_is: "<observed pattern>"
  what_should_be: "<aspiration>"
  confidence: <value>
  evidence_count: <count>
```

### Step 2: Ask for "X over Y" formulation

Use AskUserQuestion:
```
Question: Reformulate "<dim name>" as "X over Y" (Y must NOT be a strawman — must be something you genuinely could have chosen instead). Examples: "Truth over comfort", "Validity over fluency", "Long-term flourishing over short-term comfort".

Header: X over Y
Options:
  - label: "<auto-generated suggestion based on v1 what_is>"  (if you can infer)
  - label: "Skip — keep v1 only"
  - label: "Other" (user types)
```

If user picks "Skip" → flag dim as legacy-only, move on.

### Step 3: Ask for priority

Use AskUserQuestion:
```
Question: Where does this dim rank vs your other SOUL dims? (1 = most important, N = least; total order, no ties)

Header: Priority
Options:
  - label: "Top 1-3 (high)"
  - label: "Middle 4-5 (medium)"
  - label: "Bottom 6-8 (low)"
  - label: "Other (specify number)"
```

After all dims migrated, re-prompt user to assign exact 1..N (auto-detect ties + gaps).

### Step 4: Ask for inclusion test

Use AskUserQuestion:
```
Question: At least one of these 6 questions about "<dim>" — answer the one that fits best:
  1. What failure does this value prevent?
  2. What rule conflict does it resolve?
  3. What hidden judgment does it expose?
  4. What false success does it resist?
  5. Which life_OS invariant does it protect?
  6. Would the system become dangerous without it?

Header: Inclusion test
Options:
  - label: "Q1: prevents failure"
  - label: "Q2: resolves conflict"
  - label: "Q5: protects invariant"
  - label: "Other (specify Q + answer)"
```

If all 6 answers are trivial ("none really" / "I just like it") → emit warning: "This dim may not pass v2 inclusion test. Speed / elegance / output volume are NOT constitutional values. Consider moving to a personal preferences note instead. Continue anyway? [y/N]"

### Step 5: Write v2 YAML block

Append to SOUL.md (after the v1 block, with comment marker):

```yaml
---
# v2 migration for dim "<v1 name>" — added by /migrate-soul-v2 on YYYY-MM-DD
- id: dv-<auto-slug-from-formulation>
  formulation: "<user's X over Y>"
  priority: <user's pick>
  canonical_or_personal: personal
  lifecycle_stage: confirmed   # v1 -> v2 carries forward confirmed status
  source: migrated-from-v1
  created: <copy from v1 created>
  last_validated: <today>
  inclusion_test:
    <answered question>: "<user's answer>"
    # other 5 questions left blank
  failure_modes:
    known: []
    warning_signs: []
    repair_actions: []
  confidence: <copy from v1>
  evidence_count: <copy from v1>
  challenges: <copy from v1>
  what_is: "<copy from v1>"
  what_should_be: "<copy from v1>"
  gap: "<copy from v1>"
  v1_legacy: true
---
```

Do NOT delete the v1 block. Both coexist until user explicitly cleans up.

## After all dims migrated

### Re-rank priorities

Show user the proposed priority list (assigned via Step 3 buckets):
```
Proposed priority order:
  1. <dim X>  (priority 1-3 bucket)
  2. <dim Y>  (priority 1-3 bucket)
  3. <dim Z>  (priority 4-5 bucket)
  ...
```

Ask user to confirm or swap any two. Apply renumbering as 1..N (no gaps).

### Reference_set bootstrap

If SOUL.md doesn't have a `soul_reference_set` top-level block, add:
```yaml
soul_reference_set:
  aspirational: []
  anti_reference: []
  boundary_case: []
  mainstream_baseline: []
  outlier: []      # add at least 1 within 30 days — "I dislike this but it succeeds"
```

Inform user: "outlier slot must have ≥1 entry within 30 days; DREAM N3 will flag if empty."

### Final validation

Invoke `/check-soul-v2` (or call AUDITOR Mode 4 inline if slash unavailable) to verify:
- Total dim count 3-8
- Priority 1..N total order no gaps no ties
- Every confirmed dim has X-over-Y formulation
- Every dim has ≥1 inclusion_test answer non-empty
- reference_set with 5 slots exists

If pass → emit:
```
✅ /migrate-soul-v2 done.
   Migrated N v1 dims to v2 YAML.
   K dims flagged "skip" (legacy-only, will auto-deprecate 2027-05-23).
   Backup at: <SOUL_PATH>.v1-backup-<ts>
   Next: edit SOUL.md to add outlier reference within 30 days.
```

If fail → emit findings and offer to re-prompt user on failing dims.

## HARD RULES

- **Cannot run non-interactively** — every dim migration requires user confirmation per AskUserQuestion. No `--auto` flag.
- **Idempotent** — re-running on partially migrated SOUL only touches v1 dims without v2 block.
- **Never deletes v1** — both coexist during 12-month window per D3.
- **Backup mandatory** — backup file written before any edit.
- **No silent skips** — every "skip" is logged with reason; user must explicitly confirm "yes leave as legacy".
