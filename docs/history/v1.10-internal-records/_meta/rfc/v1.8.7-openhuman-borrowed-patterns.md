# v1.8.7 · OpenHuman-inspired hardening

> **方针**：让 lifeos 在自己已经对的方向上变得更强。不是用 OpenHuman 的工程哲学替换 lifeos 的工程哲学，也不是把对照表上 12 条全部移植。每条任务问一个问题：**"做了之后产品是变好还是变复杂？"** 变好的留，仅变复杂的砍。

### 1.4 · 技术栈约束（继承 v1.8.6 md-only policy + SQL 追加禁止）

v1.8.7 所有交付物**必须**是 md 文件（含 YAML frontmatter）。**禁止**引入：

- `.sql` / `.db` / `.sqlite` — 任何 SQL 数据库或本地数据库文件
- 独立 `.json` 文件（YAML frontmatter inline 在 md 中不算独立 JSON）
- `.sh` / `.bash` — shell 脚本
- `.py` — Python 文件
- `.yml` / `.yaml` — 独立配置文件

**意味着借鉴 OpenHuman 时仅借鉴 _模式_（pattern），不借鉴 _实现_（implementation）**：

| 借鉴 OpenHuman 的模式 | OpenHuman 实现（不抄） | lifeos 落地（md only） |
|---------------------|--------------------|--------------------|
| A1 L0→L1→L2 摘要折叠 | SQLite `memory_tree/chunks.db` | `_meta/sessions/L0/` + `L1-weekly/` 等目录布局 |
| B4 自驱循环 | tokio task + cron | ScheduleWakeup（Claude Code 工具，不是 lifeos 引入 sh） |
| C6 集中知识库 | `.claude/memory.md` 大文件 | `gotchas.md` 大文件（思路一致，介质相同） |
| D8 三层 rules（已砍） | JSON config 三层合并 | 即使做也只是 md frontmatter 不是 JSON |
| TokenJuice（已砍） | Rust 模块 + JSON rules | 不适用 lifeos |

**这条约束是 lifeos 核心架构承诺**——v1.8.6 已经定下，v1.8.7 重新声明以防借鉴时漂移。详见 DR-10。

### 1.5 · 本体论约束：md-only 是 lifeos 的定义性属性

用户 2026-05-25 进一步明确："**更新后的 lifeos 也只能是 md only**"。这不是 v1.8.7 一次的策略选择，是 lifeos 作为产品的**本体论约束**——

> **md-only 是 lifeos 之所以是 lifeos 的边界。** 一个引入 SQL / 独立 JSON / sh / py 的"lifeos"，不再是 lifeos——是另一个项目。

**含义**：

1. **没有 escape hatch**。不存在"如果未来某个功能 md 无法解决就破例引入 X" 这种条款。如果一个需求 md 真的解决不了，那是**重新定义需求**，不是引入新技术栈
2. **任何后续版本（v1.8.8 / v1.9 / v2.0 / 永远）都受此约束**。v1.8.7 不是规则起点而是规则的明文重述
3. **借鉴外部项目时永远只借鉴模式不借鉴技术栈**。OpenHuman 用 SQLite/JSON/Rust 不影响 lifeos 用 md
4. **可读性、可移植性、git-friendly、人眼可读可改是 lifeos 不可妥协的属性**——所有这些都依赖 md-only

**违反场景示例**（这些都不允许出现在任何未来版本）：

- ❌ "为了加速 hippocampus 检索，引入 SQLite 索引" → 用 md 索引文件
- ❌ "为了 compression rules 多源合并，引入 JSON 规则文件" → 用 md frontmatter 表达
- ❌ "为了 release verify 自动化，写 verify-release.sh" → v1.8.5 已经退役过，用 LLM-driven md command
- ❌ "为了 schema 验证，引入 yml schema 文件" → 用 md spec 描述 schema

**反过来的对照**：当 OpenHuman / 任何外部项目展示出一个新模式时，问的不是 "我们如何复刻它"，而是 "**这个模式在 md-only 下如何表达**"。表达不出来就是不引入。

### 2.1 · C6 · gotchas + memory-keeper（产品能力质变）

**当前痛点**：lifeos 现在每次踩坑（fix Notion 同步 bug / 发现 archiver 行为反直觉 / verify-release 步骤遗漏）的知识散落在各 session 文件里。下次同样情形 ROUTER 不会自动 short-circuit——要么重读历史 session（贵），要么用户手动提醒（不可靠）。

**做了之后产品获得什么**：
- 一个集中文件 `gotchas.md` 装"项目级技术坑"
- archiver wrap-up 时自动调 memory-keeper 提炼新坑
- ROUTER 接到新任务前可先扫 gotchas → 真正实现 "踩过的坑不再踩"

**交付物**：

| 文件 | 类型 | 三语 |
|------|------|------|
| `gotchas.md` | 新建（含 ≥10 条 v1.8.4-1.8.6 提炼的种子内容） | 不需要（单语 EN） |
| `agents/memory-keeper.md` | 新建 agent 定义 | 不需要 |
| `references/gotchas-spec.md` | 新建 spec：gotcha entry 格式、纳入条件、淘汰规则 | ✅ |

| `themes/*.md` | 三个主题文件各加一行 memory-keeper 角色名（六部：礼部下"史馆" / 霞が関：「記録局」 / C-Suite：Chief Memory Officer） | 主题文件本就单语 |

**关键设计**：
- gotcha entry 格式遵循 `.claude/memory.md` 的"短标题 — 行为 + 文件路径:行号 + 修复方法 (#ref)"。具体见 spec
- 种子内容：memory-keeper 第一次跑时扫 `_meta/rfc/v1.8.5-cleanup-and-hardening.md` / `v1.8.7-openhuman-borrowed-patterns.md` / `v1.9-second-brain-structure-optimization.md` + `compliance/violations.md`，提炼 ≥10 条。这同时是 memory-keeper agent 本身的功能验证
- ROUTER 在 SKILL.md 现有触发流程里增加一行 "重大任务前先扫 gotchas.md"

**产品哲学一致性**：
- ✅ md-only
- ✅ 三语（gotchas-spec 三语；gotchas.md 单语因为是项目内部知识库不是用户面对的文档）
- ✅ 走 archiver 主流程不引入新 agent 通信路径

### 2.2 · B4 · ScheduleWakeup 自驱命令（产品能力升级）

**当前痛点**：
- `verify-release` 推 tag 后要人手动多次跑确认 GitHub Release 发布、Latest 标记、9 check 全 PASS。漏一项就有 v1.8.0 那种"以为发了，其实 Latest 还在 v1.7.3"的事故（见 SKILL.md HARD RULE）

- lifeos 目前是纯 reactive 工具——用户开口才有反应

**做了之后产品获得什么**：
- 长跑任务可以"放着自己跑"，每 270 秒自动检查一次（卡在 Anthropic prompt cache 5 分钟窗口内），最多 12 ticks（60 分钟）
- lifeos 从"reactive 工具"变成"能盯任务的工具"——产品能力维度新增

**交付物**：

| 文件 | 类型 | 三语 |
|------|------|------|
| `.claude/commands/verify-release-and-watch.md` | 新建 command | 不需要（用户面命令） |
| `.claude/commands/notion-sync-and-watch.md` | 新建 command | 不需要 |
| `SKILL.md` 增加"Self-driven loops with ScheduleWakeup"章节 | 修改 | 通过 SKILL.md 主流程，已三语 |
| `references/self-driven-loops-spec.md` | 新建 spec：270s 选择理由 / 12 tick 上限理由 / 适用场景 / 跨 host 兼容 | ✅ |

**关键设计**：
- ScheduleWakeup 是 Claude Code 特有工具。command frontmatter 加 `requires_host: claude-code`；Gemini CLI / Codex CLI 见到该命令报错并指向手动版本

- 退出场景：12 tick 上限触发 → 停下来问用户（含当前状态快照、剩余未通过 check、PR/Release URL）
- 不强制要求其他长跑任务也加 watch 版本——只对真实有需求的两个（verify-release / notion-sync）做

**产品哲学一致性**：
- ✅ md-only（command 文件本身就是 md）
- ✅ 不引入新依赖
- ✅ 失败时回到 lifeos 一贯的"停下来问用户"模式

**交付物**：

**关键设计**：

### 2.8 · E9 · Status line enum 统一输出契约（产品可读性，2026-05-26 加入）

**当前痛点**：lifeos 现有 5+ 处 ad-hoc emoji status output（Pre-flight Compliance Check `🌅 Trigger`、Subagent self-check `✅ I am the X subagent`、AUDITOR 静默通过 `🔱 御史台 · 静默通过`、self-driven loop tick `🔄 tick N/12`、archiver Adjourn Confirmation `📝 Session Closed`）。每个 agent / phase 自己定格式，跨 agent 不统一，AUDITOR 验证要 grep 多种 pattern。

**做了之后产品获得什么**：
- 各 subagent 输出契约统一为：第一行必须是 status line（enum 化）
- AUDITOR 用单一 grep pattern 验证 status 合规
- 用户 / ROUTER / AUDITOR 一眼判断 agent 当前状态
- 跨 agent 状态语义一致（"acted" 在 archiver / planner / extractor 含义相同）

**Enum 设计（8 种状态）**：

| Status | Emoji | 含义 | 替代既有 ad-hoc |
|--------|-------|------|---------------|
| `starting` | 🚀 | subagent 启动，第一行 | `✅ I am the X subagent` |
| `evaluating` | 🔍 | 评估中（长 step / 推理中） | （无既有，新增） |
| `acted` | ✅ | 任务执行完成 | archiver Phase 完成 |
| `skipped` | ⏭️ | 跳过（无相关内容 / 无操作） | `🟢 silent_pass` 部分 |
| `escalated` | ⚖️ | 升级到 reviewer / council | （无既有，新增） |
| `awaiting_user` | 🟡 | 等用户确认（approval gate） | （无既有，新增） |
| `failed` | ❌ | 失败 | violation 行 |
| `silent_pass` | 🟢 | AUDITOR 静默通过（高频低噪） | `🔱 御史台 · 静默通过` |

**交付物**：

| 文件 | 类型 |
|------|------|
| ✅ `references/status-line-spec.md` 三语 | 新建：enum 定义 + 输出契约 + 22 agent migration plan + AUDITOR Mode 8 验证规则 |

- **兼容既有 ad-hoc emoji**：原有 emoji 不删，但放在 status line 之后作为辅助描述。Migration 期允许 both pattern；v1.8.8+ 移除 ad-hoc
- **agent-specific 语义**：每个 agent 在自己 .md 里声明 "我的 `acted` 等于 X / `escalated` 等于 Y"。enum 是 schema，语义由 agent 定义
- **不破 lifeos 哲学**：status enum 不限制 agent 在 status line 之后的自由输出（保留叙事性）

**产品哲学一致性**：
- ✅ md-only（spec 是 md + frontmatter）
- ✅ 三语（用户面 spec）
- ✅ 不引入新工具 / agent，仅升级既有 22 agent 的输出契约

### 2.9 · E10 · Conscious Patrol（路径 D，2026-05-26 加入）

**核心决策（DR-11）**：不做 OpenHuman 的 Subconscious tick（idle autonomous daemon），改做 **Conscious Patrol** —— retrospective Mode 0 启动时强制扫 system tasks + user tasks，输出推荐 + 用户决策。

**为什么不是 Subconscious**：
- lifeos 是 md-only skill，**没有 daemon 这一层**
- lifeos v1.8.0 明确退役 cron-style autonomy（理由：不可靠 / 不可见 / 静默数据丢失）
- 路径 A-F 深入分析后，只有路径 D（user-in-loop checkpoint）跟 lifeos 哲学完全一致

**为什么不冲突 v1.8.0 cron 退役**：
- v1.8.0 退役的是 **autonomous daemon**（cron + Python tools 跑 LLM）
- Conscious Patrol 是 **session-start user-in-loop**（每次用户开 session 时 ROUTER 主动 patrol，用户始终在前台决策）
- 本质区别：retrospective 报告"有 X 项 overdue 要不要跑？" → 用户 OK 才跑，不是 cron 静默执行
- lifeos 已经在做：v1.6.3+ retrospective Mode 0 housekeeping + session-start-inbox（v1.8.0 移到 retrospective Mode 0 inline）

**做了之后产品获得什么**：
- 把 retrospective Mode 0 隐式 patrol 行为**系统化、spec 化**
- 定义 system tasks（默认 + 用户不能删只能 disable）+ user tasks（用户加自定义 patrol items）
- 跨 session 一致：每次 session 开始 ROUTER 报告统一格式 patrol 摘要
- 跟 E9 status line 集成：每个 patrol task 输出 status enum 给用户

**System tasks 默认清单（lifeos 等价 OpenHuman 3 类）**：

| OpenHuman 默认 | lifeos 对应 |
|---------------|------------|
| "Check connected skills for errors" | Maintenance overdue 检查（10 jobs / v1.8.0+ 既有） |
| "Review new memory updates for actionable items" | Review queue overdue + SOUL drift 检查（既有）+ gotchas review（v1.8.7 新加） |
| "Monitor system health" | Compliance Watch（AUDITOR Mode 3 既有）+ wiki decay 扫描（既有） |

**User tasks 自定义机制**：
- 用户在 second-brain 加 `HEARTBEAT.md`（OpenHuman 借鉴此命名）
- 每行一个 patrol item，可选 frequency tag (`daily` / `weekly` / `monthly`)
- 例：`weekly: Check unresolved decisions older than 14 days`
- retrospective Mode 0 启动时读取并加入 patrol 清单

**决策模型（区别于 OpenHuman）**：

| OpenHuman 决策 | lifeos Conscious 决策 |
|---------------|---------------------|
| local model autonomous decide: Skip/Act/Escalate | retrospective 推荐 + 用户决策 |
| 写动作不需审批（如果用户已显式要求） | **所有 act 都需用户显式确认**（lifeos 一贯哲学） |
| Escalation card on UI for unsolicited writes | retrospective 直接报告 + ROUTER 等待用户回应 |

**交付物**：

| 文件 | 类型 |
|------|------|
| ✅ `references/conscious-patrol-spec.md` 三语 | 新建：路径 D spec + system tasks 清单 + user tasks HEARTBEAT.md 机制 + 跟 OpenHuman Subconscious 哲学区分 |
| 🔧 `SKILL.md` | 增 E10 Conscious Patrol HARD RULE |
| 🔧 `agents/retrospective.md` | Mode 0 加完整 Conscious Patrol 章节（系统化既有 housekeeping） |
| 🔧 `agents/auditor.md` | Mode 8 加 patrol compliance（除 status line 外） |

**关键设计**：
- **不引入新 cron / daemon / launchd / GitHub Actions** —— 路径 D 严格依靠 retrospective Mode 0 触发
- **不引入 external-cron 模板** —— 那是路径 E/F 的方向，v1.8.7 路径 D 不做
- **可选未来扩展**：v1.9 / v2.0 可以加路径 C/F 的 external-cron 文档化（lifeos 当 spec 提供者），但 v1.8.7 路径 D 不依赖
- **跟 E9 强绑定**：每个 patrol task 输出 status line（使用 E9 enum），AUDITOR Mode 8 双重验证

**产品哲学一致性**：
- ✅ md-only
- ✅ 三语
- ✅ 不引入 daemon / cron / 后台进程
- ✅ 用户始终在 loop（不做 autonomous）
- ✅ 不破坏 v1.8.0 cron 退役决策

## §3 · 砍掉的 3 条（理由）

### 3.1 · A2 content_hash —— 砍

**为什么砍**：lifeos 没有去重痛点。**没有任何 violations.md 条目或 session 注记提到"session 重复入库"问题**。

**如果做了之后产品发生什么**：
- session/wiki frontmatter 多一个 `content_hash: sha256:<hex>` 字段
- archiver 写入前多一个算 hash 的步骤
- archiver 多一个"hash 已存在 → 更新引用图不创建"的分支
- spec 三语镜像多一段

**问题**：上述全部成本只为防一个**不存在的**问题。这是产品复杂度增加但能力不变的典型例子——"以防万一"型设计是产品腐败的起点。

**触发重新评估的条件**：未来 lifeos 真出现 session 去重需求时（比如 second-brain runtime 跑了 2 年后出现明显重复），届时单独立项 v1.8.x 或 v1.9.x 评估。

### 3.2 · D8 三层 compression rules —— 砍

**为什么砍**：OpenHuman 的三层（builtin shipped with binary / user `~/.config/tokenjuice/` / project `.tokenjuice/`）合理是因为它有 **3 个真实独立来源**——产品作者 / 用户 / 项目维护者。

**lifeos 的情况**：你既是 builtin 作者，也是 user，也是 project maintainer。**三层来源不存在。**

**如果做了之后产品发生什么**：
- 引入"三层 compression rules"概念到 lifeos
- 新读者要理解一个"为什么 lifeos 有三层合并"的设计
- 实际只用得到一层
- spec 三语镜像多一段
- archiver / router / hippocampus 三个 agent 各加一个"应用 compression rules"的章节

**问题**：为不存在的需求引入抽象 = 产品里多一个没人用的概念 = **产品变难用**。

**触发重新评估的条件**：lifeos 未来如果真有多来源 rules（比如开源后第三方用户提交规则、企业部署有公司级 rules），届时重新设计。

### 3.3 · C7 workpad —— 砍

**为什么砍**：跟现有 sessions 的唯一区分是"agent 自主跑 vs 人机协作"——**没有用户层用途**。

**如果做了之后产品发生什么**：
- `_meta/workpad/` 新目录
- 记笔记时多一个决策"放 sessions 还是 workpad"
- archiver 需要处理两类 origin
- 搜索时要决定是否跨两类

**问题**：没有用户层用途的概念分裂 = 用户多一个决策负担 = **产品变难用**。

**替代方案**：sessions frontmatter 已有 `origin` 字段（或不难加），值可以是 `human_initiated` / `agent_autonomous`。同一目录、同一格式、同一索引——产品保持简单。

## §6 · 决策记录

### DR-10 · md-only 是 lifeos 的本体论约束（无 escape hatch）

- **决策**：lifeos 永久 md-only。v1.8.7 _以及未来所有版本_ 均不引入 SQL / 独立 JSON / sh / py / yml / yaml / db / sqlite
- **背景**：
  - v1.8.5 退役 11 bash hook + ~30 .sh 文件
  - v1.8.6 把"No py sh" 扩展为 "No py sh yml json"
  - v1.8.7 用户 2026-05-25 明确 "不要数据库 sql，不要 json，不要 sh，不要 py" + "更新后的 lifeos 也只能是 md only"——把 md-only 升级为**本体论约束**而非临时策略
- **理由**：md-only 是 lifeos 之所以是 lifeos 的定义性属性。可读性、可移植性、git-friendly、人眼可读可改、跨平台、零依赖——这些都依赖纯 md。引入任何其他文件类型就不再是 lifeos
- **影响（v1.8.7 内）**：
  - A1 cascade seal 即使未来实施，存储介质是 md 目录布局（`_meta/sessions/L0/`），不是 SQLite
  - compression rules 即使未来做（已砍），也是 md frontmatter 不是 JSON
  - B4 ScheduleWakeup 是 Claude Code 提供的 tool，不是 lifeos 自带脚本
  - memory-keeper agent 全 md 行为（读 md 写 md）
- **影响（v1.8.7 之后所有版本）**：
  - 任何提议加入新文件类型的 RFC 必须**重新定义需求**，不是寻找"md 解决不了的特例"
  - 不存在 escape hatch、不存在条件性破例、不存在"特定场景可以引入 X"的允许
  - 借鉴外部项目永远只借鉴模式不借鉴技术栈
- **触发回滚条件**：**永不**（这是本体论约束。回滚等于 lifeos 不再是 lifeos）
- **审计**：
  - verify-release check 10（新加）= grep diff 范围内的新增文件，发现任何 forbidden_extensions 立即 BLOCK release
  - SKILL.md 加入新 HARD RULE 明文化此约束（详见 §7 退出标准）
  - AUDITOR Mode 7 M7-7 在每次审计中扫描"提议中是否暗含需要 SQL/JSON/sh/py 才能工作"的设计漂移

### DR-09 · 决策标准从"工作量"换成"产品质量"

- **决策**：每条任务的去留按 "做了之后产品变好还是变复杂？" 判断
- **背景**：原 RFC 用 "10 条全做 24 工作日 vs 缩水 10 工作日" 论证，被用户纠正 "不怕费时间，要把产品做好"
- **影响**：A2 / D8 / C7 砍掉理由从"省时间"重写成"为不存在的需求引入复杂度"；A1 保留理由从"spec 先固化省得未来重写"重写成"为产品未来演化提供锚点"
- **触发回滚条件**：永不（这是元决策，下个版本继续沿用）

### DR-08 · 砍掉 cargo-cult 的 3 条不算缩水

- **决策**：A2 / D8 / C7 + Stage 7 aggressive mode 砍掉的理由是它们让产品**变臃肿但不解决痛点**，不是为了减工作量
- **背景**：用户在审议第二轮选了 "原 RFC 全量"，第三轮纠正 "做强不是替换"。综合两轮意思 = "保留 lifeos 哲学 + 砍真正的 cargo-cult"
- **影响**：本 RFC 比原全量版本少 3 条任务，但不是 "缩水版"——是 "去伪存真版"
- **触发回滚条件**：v1.8.7 ship 后 4 周内若 A2 / D8 / C7 之一出现实质用户需求，单独立项

### DR-07 · A 域 spec 验证策略

- **决策**：A1 仅写 spec 标记 status: proposal；A3 仅微调既有 concept-spec；不在 dev repo 做 mock fixture 验证
- **背景**：dev repo 无真实 sessions 数据，mock fixture 验证不等于 runtime 验证
- **影响**：v1.8.7 不动 archiver 关于 cascade seal 的代码；A1 实施留待 Jason 在 second-brain 跑过 5-10 次后立 v1.9
- **触发回滚条件**：second-brain 跑通后 v1.9 / v2.0 立项时按本 spec 实施

### DR-06 · 升级走 zero-friction，无 migrate 命令

- **决策**：v1.8.7 升级不引入 `/migrate-v1-8-7` 命令；archiver 第一次跑自动建新文件夹
- **背景**：没有 schema/目录布局变更（A2 砍了），不需要专门迁移命令；原 RFC 的三模式（conservative/hash-only/aggressive）随 A2/A1 砍掉自然消失
- **影响**：MIGRATION.md 只加 5 行；新用户升级体验 = 4 步命令
- **触发回滚条件**：未来版本若真有 schema 变更（如 v2.0 实施 cascade seal）届时重新评估

### DR-05 · F11 三语 diff check 先 WARN 后 BLOCK

- **决策**：v1.8.7 check 9 是 WARN 级
- **理由**：第一次跑会暴露大量历史漂移，先看真实数据
- **触发回滚条件**：v1.8.7 ship 后 4 周内 WARN 输出可枚举 → v1.8.8 升 BLOCK

### DR-04 · archiver.md 行数管理

- **决策**：v1.8.7 不拆 archiver.md（955 → ~1050 行，未到拆分阈值）
- **触发拆分条件**：超过 1200 行
- **拆分方案**（届时启用）：`agents/archiver/<phase>.md` 子目录，主 archiver.md 保 phase 总览 + 链接

### DR-03 · 三语镜像范围

- **决策**：所有用户面 spec（references/*.md）和 用户面文档（WHEN-NOT-TO-ADD、MIGRATION）三语；项目内部知识库（gotchas.md）单语英文
- **理由**：三语承诺面向 lifeos 用户；内部 dev knowledge base 不在承诺范围内
- **触发回滚条件**：若中日用户反馈 gotchas.md 阅读困难，单独追加翻译

### DR-02 · v1.8.7 沿用 patch 编号

- **决策**：尽管增加 7 条功能，仍按 patch（v1.8.7）
- **背景**：v1.8.5 / v1.8.6 已开先例（功能性变更按 patch 编号）；v1.8.7 实际不是 breaking change（archiver 行为兼容 v1.8.6）
- **触发回滚条件**：v2.0 主版本切换时一次性补 SemVer

### DR-11 · E 域决策反转：v1.8.7 内做 E9 + E10 路径 D（2026-05-26）
