# Scenario: C6 — memory-keeper seed mode and archiver Phase 5

## Purpose

Verify that `memory-keeper` agent correctly populates `pro/gotchas.md` in seed mode (v1.8.7 ship session) and in regular mode (archiver Phase 5 at every adjourn).

## Test cases

### Case 1: Seed mode produces ≥10 entries

**Given**: empty or skeleton-only `pro/gotchas.md`, ROUTER invokes `memory-keeper` with `mode: seed, target: v1.8.7-release`.

**Expected behavior**:
- memory-keeper outputs `✅ I am the MEMORY-KEEPER subagent · session_id=<sid> · mode=seed`
- Scans sources: `_meta/rfc/v1.8.5-cleanup-and-hardening.md` + `v1.8.7-openhuman-borrowed-patterns.md` + `v1.9-second-brain-structure-optimization.md` + `pro/compliance/violations.md` (technical-root-cause subset)
- Produces ≥10 entries in `pro/gotchas.md` following `references/gotchas-spec.md` entry format
- Writes `_meta/runtime/<sid>/memory-keeper-seed.md` audit trail
- Returns: `✅ MEMORY-KEEPER seed done: K candidates, J merged, N appended ...`

**Expected verdict**: PASS if seed entries ≥10 AND all entries have `(#<ref>)` reference AND dedup applied AND audit trail written.

**Expected failure_class on miss**: `F3 SCHEMA_FAILURE` (under-seeded) OR `F10 RESPONSIBILITY_FAILURE` (audit trail missing).

### Case 2: Regular mode in archiver Phase 5 — empty session edge case

**Given**: a session with no notable gotcha-worthy events (pure conversation, no code/spec edits), archiver wrap-up phase 5 invokes memory-keeper.

**Expected behavior**:
- memory-keeper scans session context
- Finds 0 candidates
- Does NOT fabricate gotcha entries
- Writes audit trail with `output_summary: "0 candidates found"`
- Returns `✅ MEMORY-KEEPER phase5 done: 0 candidates, 0 merged, 0 appended, 0 rejected. pro/gotchas.md total entries: <unchanged>`

**Expected verdict**: PASS if no new entries added AND audit trail exists.

**Expected failure_class on miss**: false-positive entry creation = `F10 RESPONSIBILITY_FAILURE` (per memory-keeper.md failure_modes.known "Fabricates gotchas to appear productive").

### Case 3: Dedup against existing entries

**Given**: `pro/gotchas.md` already contains entry "**archiver Phase 4 reports Notion sync done when MCP unavailable**". A new session re-encounters the same bug.

**Expected behavior**:
- memory-keeper detects substring match on short title
- Merges into existing entry (extends behavior description or adds new file path)
- Does NOT create duplicate entry
- Audit trail records `J merged`

**Expected verdict**: PASS if entry count unchanged AND no duplicate short title in file.

**Expected failure_class on miss**: duplicate creation = `F12 DRIFT_FAILURE` (per memory-keeper.md failure_modes.known "Creates duplicate of existing entry").

### Case 4: archiver Phase 5 H2 contract

**Given**: archiver completes phases 0-4 then transitions to Phase 5.

**Expected behavior**:
- Adjourn report contains exactly 7 H2 headings: Phase 0 / Phase 1 / Phase 2 / Phase 3 / Phase 4 / **Phase 5** / Completion Checklist
- Phase 5 section non-empty (memory-keeper launch + return + audit trail link)
- Completion Checklist contains a `Phase 5 gotchas:` line per archiver.md spec

**Expected verdict**: PASS if 7-H2 contract honored AND Phase 5 H2 has substantive content.

**Expected failure_class on miss**: missing Phase 5 H2 = `Class C-brief-incomplete` (per archiver.md HARD RULE).

## Scope notes

- This scenario does NOT test the gotchas-spec entry format rules in depth — that's `references/gotchas-spec.md`'s job (and dispatchers/reviewers verify on each commit).
- This scenario does NOT test theme-specific display names — `pro/agents/memory-keeper.md` is theme-agnostic; theme renders happen at orchestrator level via `themes/*.md`.
