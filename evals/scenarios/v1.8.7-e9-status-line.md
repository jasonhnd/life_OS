# Scenario: E9 — Status Line output contract

## Purpose

Verify all subagents emit status lines per the 8-enum contract; AUDITOR Mode 8 catches violations.

## Test cases

### Case 1: starting line format (M8-1)

**Given**: archiver invoked for adjourn.

**Expected behavior**:
- First non-blank line of transcript: `🚀 starting · archiver · fresh adjourn invocation, trigger 1, 5-phase flow starting`
- Matches regex `^🚀 starting · <agent-id> · .+`

**Expected verdict**: PASS.

**Expected failure_class on miss**: `F3 SCHEMA_FAILURE: missing or malformed starting status line`.

### Case 2: Closed enum (M8-2)

**Given**: agent invents new status keyword (e.g. `🤔 thinking · planner · ...`).

**Expected behavior**:
- AUDITOR Mode 8 detects keyword `thinking` not in `{starting, evaluating, acted, skipped, escalated, awaiting_user, failed, silent_pass}`
- Emits `F4 SCOPE_FAILURE: invented status keyword <thinking>` to violations.md

**Expected verdict**: FAIL (correct AUDITOR behavior).

### Case 3: Emoji/keyword pairing (M8-3)

**Given**: agent emits `✅ failed · auditor · ...` (mismatched emoji + keyword).

**Expected behavior**:
- AUDITOR Mode 8 detects: `✅` expected with `acted`, NOT `failed`
- Emits `F3 SCHEMA_FAILURE: emoji/status mismatch`

**Expected verdict**: FAIL detected.

### Case 4: Per-agent enum declaration (M8-4)

**Given**: New agent added without `## Status Output (E9)` section in agent .md.

**Expected behavior**:
- AUDITOR Mode 8 reads agents/*.md
- Detects missing `## Status Output (E9)` header
- Emits `F3 SCHEMA_FAILURE: incomplete Status Output declaration in <agent>.md`
- During v1.8.7 migration window: WARN level (not BLOCK)
- v1.8.8+: BLOCK level

**Expected verdict (v1.8.7)**: WARN. **(v1.8.8)**: FAIL.

### Case 5: Multi-status transitions (M8-5)

**Given**: archiver runs Phase 0 → 1 → 2 → 3 → 4 → 5 successfully.

**Expected behavior**:
- 6+ status lines emitted (one starting + transitions per phase)
- Each phase transition has its own status line
- AUDITOR Mode 8 counts status lines vs expected transitions

**Expected verdict**: PASS if ≥6 status lines across the invocation.

**Expected failure_class on miss**: `F8 SILENT_FAILURE: agent skipped status emission at transition`.

### Case 6: Failed status classification (M8-6)

**Given**: agent emits `❌ failed · finance · ...` without F-class reference.

**Expected behavior**:
- AUDITOR Mode 8 greps description for F-class pattern (F1-F17 or A/B/C/D/E)
- No match → `F10 RESPONSIBILITY_FAILURE: failed status without classification`

**Expected verdict**: FAIL detected.

### Case 7: Migration window WARN tolerance (v1.8.7 only)

**Given**: agents in mid-migration; 15 still use v1.8.6 ad-hoc emoji patterns (`✅ I am the X subagent`); 7 use new v1.8.7 status line.

**Expected behavior**:
- AUDITOR Mode 8 detects mixed patterns
- v1.8.7 migration window: WARN level (lists agents pending migration, does NOT block release)
- v1.8.8+ (whenever): BLOCK level (mixed patterns → release halt)

**Expected verdict (v1.8.7)**: WARN. Release proceeds. **(v1.8.8)**: FAIL. Release blocked.

## Scope notes

- This scenario validates the contract, not the per-agent semantic correctness (which the agent's own `## Status Output (E9)` table documents).
- AUDITOR Mode 8 M8-4 in v1.8.7 is WARN-level by design — agents transitioning to new contract.
- Real runtime verification deferred (need actual subagent invocations with audit trails in `_meta/runtime/<sid>/`).
