# Scenario: v1.9 methods/decisions/journal cross-reference fields

## Purpose

Verify Opt #8 (Q-meta-4 / DR-1.9.13 + Q-undecided-11 / DR-1.9.24) correctly establishes single-directional frontmatter fields across the three artifact types, and reverse queries use Dataview + Recent 5 wikilinks pattern (no maintained `applied_in_decisions` field).

---

## Test cases

### Case 1: Stage 7 frontmatter field backfill

**Given**:
- After Stages 1-6 of `/migrate-v1.9`, vault contains:
  - `meta/methods/iterative-doc-refinement.md` (4 existing methods)
  - `meta/decisions/<YYYY-MM>/*.md` (decisions just migrated from Stage 2)
  - `meta/journal/<date>.md` files (just merged from Stage 4)

**Expected behavior** (Stage 7):
- Every `meta/methods/*.md` has frontmatter field:
  - `born_from_decisions: []` (empty list if missing original data)
- Every `meta/decisions/<YYYY-MM>/*.md` has:
  - `applied_methods: []` (empty list if not specified)
  - `journal_date: <YYYY-MM-DD>` (derived from reviewed_at)
- Every `meta/journal/<date>.md` has:
  - `referenced_decisions: []`
  - `referenced_methods: []`

**Expected verdict**: PASS if all three artifact types have new fields + correct types (list vs string)

**Expected failure_class on miss**:
- Missing field in any artifact = `F4 SCOPE_FAILURE`
- Wrong type (e.g., `applied_methods: <single-string>` instead of `[]`) = schema violation

### Case 2: NO `applied_in_decisions` field on method files (Q-11 / DR-1.9.24)

**Given**:
- After migration, `meta/methods/iterative-doc-refinement.md`

**Expected behavior**:
- Frontmatter has `born_from_decisions: [...]`
- Frontmatter does **NOT** have `applied_in_decisions:` field
- Body has `## Applied in decisions` section with Dataview block + Recent 5 wikilinks fallback (matches project index pattern)

**Expected verdict**: PASS if `applied_in_decisions` field is absent AND `## Applied in decisions` section exists with both Dataview and wikilinks

**Expected failure_class on miss**:
- `applied_in_decisions:` field present = `F4 SCOPE_FAILURE` (DR-1.9.24 violated)
- Missing `## Applied in decisions` section = `F4 SCOPE_FAILURE` (inconsistent with project index symmetry)

### Case 3: Method page Dataview reverse query

**Given**:
- After migration, `meta/methods/iterative-doc-refinement.md` has the `## Applied in decisions` section
- Multiple decisions in `meta/decisions/` reference this method via `applied_methods: [iterative-doc-refinement]`

**Expected behavior** (when user opens method file in Obsidian with Dataview installed):
- Dataview block queries `meta/decisions/` for matching `applied_methods`
- Returns table of: type, reviewed_at, decision text
- Sorted by reviewed_at DESC
- LIMIT 20 (per Q-16.2 default)

**Expected verdict**: PASS if Dataview query returns matching decisions (manual Obsidian test) OR equivalent grep-based check confirms structure

### Case 4: Best-effort journal.referenced_decisions backfill

**Given**:
- After Stage 7, a journal entry `meta/journal/2025-03-15.md` exists
- A decision migrated from Stage 2 has `journal_date: 2025-03-15` and id `dec-2025-03-15-001`

**Expected behavior** (Stage 7 step 3, best-effort):
- `meta/journal/2025-03-15.md` frontmatter `referenced_decisions:` contains `dec-2025-03-15-001`

**Expected verdict**: PASS if best-effort backfill happened AND decision id added to journal's referenced_decisions

**Note**: This step is **best-effort** per RFC §3.8.3 step 3 — failures here do not block migration. If a journal has wrong/missing referenced_decisions field, future archiver runs will correct.

### Case 5: Future decision write — agent populates fields correctly

**Given**:
- Post-migration, user runs a new full-deliberation session that ends with a decision
- archiver Phase 1 writes the new decision

**Expected behavior**:
- New decision file at `meta/decisions/<YYYY-MM>/<id>.md` has:
  - `applied_methods: [<methods used>]` (if any) — list, may include zero or multiple
  - `journal_date: <today>` — matches the session's adjourn date
- `meta/journal/<today>.md` frontmatter:
  - `referenced_decisions:` includes new decision id
  - `referenced_methods:` includes methods used (if archiver / knowledge-extractor identified any)
- Method file's `## Applied in decisions` section auto-updates if archiver maintains the Recent 5 wikilinks

**Expected verdict**: PASS if fields populated correctly AND no `applied_in_decisions` field appears (forbidden per DR-1.9.24)

**Expected failure_class on miss**:
- `applied_methods` written as string instead of list = schema violation
- archiver creates `applied_in_decisions` field on method file = `F4 SCOPE_FAILURE`

## Failure taxonomy reference

| ID | Class | When applicable |
|----|-------|----------------|
| F4 | SCOPE_FAILURE | Schema field missing, wrong type, forbidden `applied_in_decisions` resurrected |
| F10 | RESPONSIBILITY_FAILURE | Stage 7 silently skipped, fields not populated post-migration |

---

## Notes

- DR-1.9.24 is strict: `method.applied_in_decisions:` field MUST NOT exist anywhere post-v1.9
- Reverse queries from method → decisions use Dataview + Recent 5 wikilinks pattern (consistent with project index)
- `journal_date` field on decisions enables: (a) journal-to-decision backlinks, (b) "what did I decide that day" queries
